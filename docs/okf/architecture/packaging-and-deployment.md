# Purpose

Packaging preserves deterministic contracts and fast startup without locking the first milestone into a premature single-binary format.

# Application pack v1

Logical contents:

```text
QPACK
├── metadata
├── application source or bytecode
├── handler table metadata
├── route pipelines
├── schema/serializer IR
├── capability requirements
├── source maps
├── contract hash
└── integrity records
```

The physical format may initially be a directory or simple archive for inspectability.

# Metadata

```json
{
  "qpackVersion": 1,
  "frameworkVersion": "0.1.0-dev",
  "compilerVersion": "0.1.0-dev",
  "runtimeAbi": 1,
  "engine": "quickjs-ng",
  "engineVersion": "...",
  "engineBytecodeAbi": "...",
  "target": "x86_64-unknown-linux-gnu",
  "profile": "serverless",
  "contractHash": "sha256:...",
  "contentHash": "sha256:..."
}
```

Unknown incompatible versions fail before ready.

# Artifact modes

## Directory pack

Best for M1/M2:

- transparent;
- easy to diff;
- easier source maps;
- simple iteration.

## Packed archive

Useful after the format stabilizes:

- one application resource;
- integrity verification;
- memory mapping or efficient reads.

## Single executable

Later packaging:

```text
q build --standalone
```

Embeds the runtime and application pack into one platform-specific executable.

This is a deployment convenience, not a reason to duplicate compiler/runtime logic.

# Platform targets

Initial:

```text
Linux x86_64
Linux aarch64
```

macOS may be supported for development. Windows and musl/static targets are evidence-driven later decisions.

# Configuration

Runtime configuration follows explicit precedence:

```text
command-line arguments
environment variables
configuration file
pack defaults
```

Secrets are never embedded by default.

Configuration schema includes:

- address/port;
- profile;
- limits;
- logging;
- readiness/shutdown;
- capability settings;
- service settings;
- trust/proxy policy.

Invalid production configuration fails closed.

# Container image

Recommended structure:

```text
minimal runtime image
non-root user
read-only application pack
writable temp only if required
no compiler/Bun/node_modules
health/readiness endpoints
graceful stop signal
```

The first deliverable may include a reproducible Dockerfile, but container startup is measured separately from bare process startup.

# Deployment readiness

Liveness answers only whether the process/host is alive.

Readiness verifies:

- pack loaded;
- engine worker ready;
- listener available;
- required eager services healthy;
- no fatal compatibility mismatch.

Lazy optional services do not make readiness fail unless route availability policy requires them.

# Updates

An application update is a new immutable pack/version. In-place mutation of the loaded manifest is not supported initially.

Possible service deployment process:

```text
build and verify pack
→ start new process
→ readiness
→ shift traffic
→ drain old process
```

Hot reload is a development feature, not a production consistency mechanism.

# Supply-chain integrity

The release pipeline records:

- source commit;
- lockfile;
- Rust dependency lock;
- Bun/tool versions;
- compiler/runtime artifact hashes;
- application pack hash;
- SBOM/license report;
- test/benchmark evidence IDs.

Signature verification is recommended before public release. Hash verification is mandatory in the initial pack loader.

# Bytecode trust

Release bytecode:

- is generated by the project's pinned build;
- is never accepted from a request;
- has exact engine ABI metadata;
- is integrity checked;
- cannot silently fall back to a different interpretation mode.

# Rollback

Rollback deploys a previously verified application/runtime pair. Because engine bytecode is version-bound, the pack and compatible runtime must be retained together.

Contract rollback considerations are reported by semantic diff; a runtime rollback does not erase external data/API compatibility consequences.

# Acceptance criteria

- clean runtime artifact has no Bun, TypeScript compiler, or source package manager dependency;
- invalid/altered pack fails before ready;
- engine/bytecode mismatch fails clearly;
- directory pack reproduces the same manifest hashes across identical builds;
- non-root container runs and shuts down gracefully;
- source maps work from packaged artifacts;
- standalone packaging, when added, passes the same conformance suite;
- release metadata links tests and benchmark evidence.
