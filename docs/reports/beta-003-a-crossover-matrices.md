# BETA-003-A — Crossover Matrices: 0/1/5/10/25ms I/O, Payloads, CPU Operation Levels

Status: **MEASURED** (generated evidence) + **DRAFT wording** (see last
section; not approved public positioning). Scope: the four real-world JS/TS
candidates (`bun-fetch`, `hono` on Bun; `elysia2` on Bun; `fastify` on
Node 22). The Velqu candidate is not part of these matrices; its cold-start
and crossover behavior is measured by BETA-003-B/C on the loopback harness.

## Reproducible method

- Command (from `benchmarks/real-world/`):
  `./run-crossover.sh 3 1,10` — starts the controlled upstream
  (`upstream.ts` on 127.0.0.1:8791), then for each candidate boots a fresh
  server on a free port and drives 13 cells at c=1 and c=10 for 3s per cell:
  - I/O latency matrix: `W4_0ms` .. `W4_25ms` (`GET /api/bench/io?ms=N`)
  - Payload matrix: `PAYLOAD_1/10/20/50` (`GET /api/products?...&limit=N`)
  - CPU operation levels: `CPU_0/100/1000/10000`
    (`GET /api/bench/cpu?ops=N`; the identical `cpuWork` loop is shared by
    every candidate from the matched contract module — the only variable is
    the execution engine)
- Contract gate: every candidate passed the full `verify-contract.ts`
  fixture matrix (including the new `cpu.*` fixtures with checksum oracle =
  the same shared `cpuWork`) before this run.
- Raw evidence: `benchmarks/raw/real-world/crossover/<candidate>/`
  (`summary.json`, retained byte-reproducible `raw.jsonl.gz`, `RETENTION.md`);
  comparison reports `w4-latency.md`, `payload-matrix.md`, `cpu-matrix.md`
  are generated by `compare-w4.ts` — no hand-typed values.
- Environment (from the summaries): Bun 1.4.0, Node v22.23.2, linux/x64,
  repo commit `b04e72a` (the master head this packet branched from).
- Reproducibility caveat: the raw numbers below are one run on a shared
  development host. The method is reproducible; a canonical claim needs a
  quiet-host rerun (BETA-014 owns the canonical report).

## Cold / warm / CPU / I/O are not conflated

- **I/O cells** isolate upstream latency (deterministic timer in the shared
  upstream) from handler work.
- **CPU cells** contain zero I/O — the handler runs a bounded deterministic
  loop and returns a checksummed JSON body.
- **Payload cells** are pure serialization size scaling on the W3 route.
- Cold-start behavior is out of scope here entirely (BETA-003-B).

## Results

### I/O latency matrix (0/1/5/10/25ms)

Generated: `benchmarks/raw/real-world/crossover/w4-latency.md` (all cells:
0 errors, 0 status mismatches, p99 within the structural sanity bounds).
Reading at c=1: every candidate's p50 rises by the nominal upstream latency
(e.g. the 25ms cells show p50 ≈ 25–26ms across candidates) — the cells
measure what they claim to measure, and no candidate is distinguishable from
another at higher upstream latencies; the 0ms cell exposes the per-candidate
overhead floor (p50 ≈ 30–40µs for Bun candidates, ≈ 40–60µs for Node).

### Payload matrix (limit 1/10/20/50)

Generated: `benchmarks/raw/real-world/crossover/payload-matrix.md` (all
cells: 0 errors, 0 mismatches). At c=1 every candidate loses roughly an
order of magnitude (or more) of throughput from `PAYLOAD_1` to `PAYLOAD_50`
(e.g. bun-fetch 7106 → 410 rps; fastify 11166 → 474 rps): response
serialization size, not routing or the engine, dominates these cells.

### CPU operation levels (0/100/1000/10000 iterations)

Generated: `benchmarks/raw/real-world/crossover/cpu-matrix.md` (all cells:
0 errors, 0 mismatches). At c=1, throughput from `CPU_0` to `CPU_10000`
falls by 1.6× (bun-fetch 18832 → 11580 rps; fastify 20344 → 12664 rps) to
2.2× (hono 22497 → 10249 rps; elysia2 22581 → 10328 rps). Server RSS
sampled per candidate run: Bun candidates 43–55 MB, Node/Fastify ~165 MB.

## Positioning (follows the evidence above; measured-run scope)

1. At controlled upstream latencies ≥ 5ms, candidates are
   indistinguishable — latency is dominated by the upstream, as designed.
2. Candidate-to-candidate differences appear at the overhead floor (0ms
   cell) and in pure-handler-work cells, where execution engine and runtime
   serialization dominate.
3. Response payload size dominates all handler-side costs beyond ~10KB
   bodies in these cells.
4. Resident memory differs by runtime (Node > Bun for these candidates) —
   sampled, single-run, shared host.
