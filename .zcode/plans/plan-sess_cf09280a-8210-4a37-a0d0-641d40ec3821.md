## M25-002-A implementation plan — compare codec strategies

### Scope and decision
Implement a benchmark-only, schema-aware projection candidate without changing production `ResponseStrategy`, `RoutePlan`, compiler strategy selection, or runtime fallback behavior. The current production tree has only QuickJS and generic native conversion; direct byte scanners/decoders belong to M25-003/M25-004. Strategy C will therefore be explicitly labeled **generated schema-aware projection prototype**: generated fixed-schema decode/projection over the parsed JSON value, followed by the same host/QuickJS boundary used by the benchmark. The report will state that it is not the production direct decoder and that no global strategy is selected in A.

### 1. Extend the benchmark model
- Add a benchmark-local candidate enum and metadata in `crates/q-bench-support/src/bin/bridge_bench.rs` (or a small adjacent module) for:
  - `quickjs-json`: raw bounded bytes enter QuickJS and use `JSON.parse`/handler/`JSON.stringify`.
  - `generic-rust`: `serde_json::from_slice`, recursive host-to-QuickJS conversion, handler, and native traversal/serialization.
  - `generated-schema`: `serde_json::from_slice` followed by generated schema-specific projection functions for the frozen benchmark schemas, then the same host-to-QuickJS invocation path.
- Keep candidate names and stage boundaries explicit in raw records; do not silently call the prototype a production codec.
- Preserve single-worker ownership and existing generous benchmark deadlines.

### 2. Add deterministic schema-aware benchmark fixtures
- Define a small, nested, and array-record Schema IR v2 corpus using existing `q-schema-runtime::SchemaIr` forms (object, integer, string, boolean, array, optional/nullable where applicable).
- Add generated projection functions for those exact schemas, with checked required fields, type checks, optional/null handling, and deterministic output ordering. Generate the functions from a compact benchmark schema declaration or a clearly marked generated module so the source and emitted result are reproducible.
- Ensure unsupported IR nodes and fallback-without-inner are recorded as unavailable/failed-closed rather than benchmarked as successful generated codecs.
- Add correctness parity checks against the existing QuickJS and generic candidates for every fixture before timing samples.

### 3. Capture reproducible raw evidence
- Extend the bridge benchmark output to retain one JSONL row per candidate/case/sample with at least:
  - candidate, schema/case, sample index, total microseconds, and correctness;
  - input byte length and output byte length;
  - stable run id, engine/version, iteration count, warmup count, and benchmark source/prototype identifier.
- Extend the summary with `n`, mean, p50, p95, p99, correctness/failure counts, and candidate availability. Do not claim CPU/allocation conclusions in A; those are M25-002-C.
- Use a deterministic case order and fixed seed/run metadata. Keep the existing A/B bridge data intact or migrate it into the new versioned M25-002 raw directory without overwriting historical M1 evidence.
- Hash the benchmark executable, generated benchmark source/module, raw JSONL, and summary with SHA-256. Record those hashes in the strategy report and a benchmark-local evidence manifest; do not rewrite the canonical root benchmark manifest until matched evidence and the later C/D packets justify it.

### 4. Add correctness and reproducibility tests
- Add Rust unit tests for each generated projection: valid values, missing required fields, wrong scalar types, nested/array item failures, optional/null behavior, and output equivalence with the reference JSON.
- Add a deterministic test that runs the same fixture through all available candidates and compares normalized JSON output and error classification.
- Keep existing `q-engine-quickjs`, `q-schema-runtime`, fuzz, and Bun conformance tests unchanged except for the smallest necessary fixture/helper additions; no timing assertions in conformance tests.

### 5. Produce the A strategy report
- Add a new report such as `docs/reports/m25-002-a-strategy-comparison.md` rather than rewriting the historical M1 bridge report.
- Document:
  - exact command, host/toolchain/QuickJS versions, warmup/iterations, case matrix, and raw paths;
  - fairness limitations (prototype C still parses with serde_json; direct byte scanning is deferred);
  - per-candidate p50/p95/p99 and correctness status from the committed summary;
  - artifact hashes and generated-source identity;
  - explicit statement that A provides measurement evidence only and does not select a global strategy or make unsupported performance claims.
- Add the report/raw paths to the benchmark-local evidence manifest or existing report index only where the current schema supports it.

### 6. Verification and delivery
- Run targeted commands required by M25-002-A:
  - `cargo test -p q-engine-quickjs`
  - `cargo test -p q-schema-runtime`
  - `bun test`
  - `bun run typecheck`
- Build the release benchmark with the repository’s reproducibility remapping (`scripts/benchmark` conventions), run the new benchmark, retain raw JSONL/summary, compute hashes, and verify no benchmark manifest is changed without matched evidence.
- Run `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `scripts/validate-okf`, and the benchmark-local validator/checks before commit.
- Mark only M25-002-A PASS in its packet after all evidence is present; leave M25-002-B/C/D and all later packets TODO.
- Commit one atomic packet on `m25-002-a`, push, open the PR with `Closes #126`, document any zero-step CI infrastructure failure honestly, and squash-merge only after local evidence is complete.

### Files expected to change
- `crates/q-bench-support/src/bin/bridge_bench.rs` and/or a new benchmark-local generated codec module.
- `crates/q-bench-support/Cargo.toml` only if a direct dependency is required (prefer existing dependencies).
- New versioned raw/summary evidence under `benchmarks/raw/` plus a benchmark-local hash manifest.
- New `docs/reports/m25-002-a-strategy-comparison.md`.
- M25-002-A task record and, if needed, its generated status/index bookkeeping after evidence is complete.

### Explicit non-goals
- No production generated decoder/encoder implementation.
- No changes to `ResponseStrategy`, compiler RoutePlan metadata, production fallback behavior, or public contract projections.
- No CPU/allocation profiling or final strategy selection (M25-002-C/D).
- No benchmark manifest rewrite or performance claim without matched raw evidence.
